# Manual Testing Instructions: Story 1.1 - Complete MQTTManager Implementation

## Test Environment Setup

### Hardware Requirements
- ESP32 Development Board (ESP32-WROOM-32 or compatible)
- USB cable for Serial Monitor connection
- WiFi router/access point
- Computer with Serial Terminal software

### Software Tools Needed
- **MQTT Explorer** (https://mqtt-explorer.com/) - for monitoring MQTT messages
- **PlatformIO** - for uploading firmware and Serial Monitor
- **HiveMQ Cloud Console** or local MQTT broker (Mosquitto)
- **Terminal/PuTTY** - for Serial communication at 115200 baud
- **Web browser** - Chrome/Firefox for accessing device web interface

### Network Configuration
- Stable WiFi network (2.4GHz)
- Internet access for cloud MQTT broker OR
- Local MQTT broker accessible on same network
- Device and testing computer on same network segment

### MQTT Broker Setup
1. **Option A: HiveMQ Cloud (Recommended for testing)**
   - Create free account at https://www.hivemq.com/mqtt-cloud-broker/
   - Note down: Broker URL, Port (8883), Username, Password
   - Download CA certificate if required

2. **Option B: Local Mosquitto Broker**
   ```bash
   # Install Mosquitto
   sudo apt-get install mosquitto mosquitto-clients

   # Configure for anonymous access (testing only)
   echo "allow_anonymous true" | sudo tee -a /etc/mosquitto/mosquitto.conf
   sudo systemctl restart mosquitto
   ```

## Test Procedures

### Test Case 1: MQTT Manager Singleton Initialization
**Objective**: Verify MQTTManager initializes correctly as singleton

**Steps**:
1. Power on ESP32 and open Serial Monitor
2. Watch for initialization messages
3. Look for: `[INFO] MQTT: Manager initialized`
4. Note heap usage after init: __________ bytes
5. Verify no duplicate initialization messages

**Expected Result**:
- Single initialization message
- Heap increase < 5KB
- No crash or restart

**Failure Scenarios**:
- Multiple initialization messages → Singleton pattern failed
- Heap increase > 5KB → Memory leak in constructor
- Crash/restart → Null pointer or allocation failure

### Test Case 2: MQTT Broker Connection
**Objective**: Validate successful connection to MQTT broker

**Steps**:
1. Navigate to device web interface: `http://[device-ip]/settings-mqtt.html`
2. Configure MQTT settings:
   - Enable MQTT: ✓
   - Broker: [your-broker-address]
   - Port: 8883 (TLS) or 1883 (non-TLS)
   - Username: [your-username]
   - Password: [your-password]
   - Client ID: ESP32_[MAC-last-6]
   - Use TLS: ✓ (if using port 8883)
3. Click "Save Configuration"
4. Monitor Serial output for connection sequence
5. Open MQTT Explorer and connect to same broker
6. Look for client connection in broker logs

**Expected Result**:
```
[INFO] MQTT: Connecting to broker: your-broker.hivemq.cloud:8883
[INFO] MQTT: TLS enabled, configuring certificates
[INFO] MQTT: Connected successfully
[INFO] MQTT: State changed: MQTT_DISCONNECTED → MQTT_CONNECTING → MQTT_CONNECTED
```

**Failure Scenarios**:
- `[ERROR] MQTT: Connection timeout` → Network issue or wrong broker
- `[ERROR] MQTT: Authentication failed` → Wrong credentials
- `[ERROR] MQTT: TLS handshake failed` → Certificate issue

### Test Case 3: Test Counter Publishing
**Objective**: Verify test counter publishes every 10 seconds

**Steps**:
1. Ensure MQTT connected (Test Case 2 passed)
2. In MQTT Explorer, subscribe to `tempcontroller/telemetry/test`
3. Start timer/stopwatch
4. Wait for first message to appear
5. Verify message format:
   ```json
   {
     "counter": 0,
     "uptime": 123,
     "heap": 145678
   }
   ```
6. Wait for next message and verify:
   - Counter incremented by 1
   - Timing is 10 seconds ±1 second
7. Monitor for 5 minutes (30 messages)

**Expected Result**:
- Messages arrive every 10 seconds consistently
- Counter increments sequentially
- Heap remains stable (±2KB variation)

**Failure Scenarios**:
- Missing messages → Publishing failed
- Irregular timing → Timer issue
- Counter gaps → Message queue overflow

### Test Case 4: Connection State Display
**Objective**: Verify connection status shown on Serial output

**Steps**:
1. With MQTT connected, monitor Serial output
2. Type command in Serial: `mqtt.status`
3. Verify detailed status output appears
4. Note all status fields populated correctly
5. Disconnect WiFi (unplug router or disable WiFi)
6. Watch for disconnection message within 30 seconds
7. Reconnect WiFi
8. Monitor reconnection sequence

**Expected Result**:
```
=== MQTT Status ===
Enabled: Yes
State: MQTT_CONNECTED
Connected: Yes
Broker: broker.hivemq.cloud:8883
Client ID: ESP32_A1B2C3
TLS: Enabled
Uptime: 300 seconds
Messages Sent: 30
Messages Failed: 0
Reconnect Count: 0
Memory Used: 25432 bytes
==================
```

**Failure Scenarios**:
- No status output → Command handler not working
- State mismatch → State machine error
- Memory continuously increasing → Memory leak

### Test Case 5: Automatic Reconnection
**Objective**: Validate exponential backoff reconnection

**Steps**:
1. Establish MQTT connection
2. Block MQTT port on router/firewall to simulate broker offline
3. Monitor Serial for disconnection detection
4. Note reconnection attempts and timing:
   - 1st attempt: _____ seconds
   - 2nd attempt: _____ seconds
   - 3rd attempt: _____ seconds
   - 4th attempt: _____ seconds
5. Verify exponential backoff (1s, 2s, 4s, 8s, 16s, 32s, max 60s)
6. Unblock MQTT port
7. Verify successful reconnection
8. Check `mqtt.status` shows correct reconnect count

**Expected Result**:
- Exponential delays between attempts
- Maximum delay caps at 60 seconds
- Successful reconnection when broker available
- State transitions logged correctly

**Failure Scenarios**:
- Immediate retry spam → No backoff implemented
- Never reconnects → Reconnection logic broken
- Crashes during reconnection → Exception handling missing

### Test Case 6: Heap Memory Monitoring
**Objective**: Verify memory usage stays within limits

**Steps**:
1. Note initial heap before enabling MQTT: __________ bytes
2. Enable MQTT and connect
3. Note heap after connection: __________ bytes
4. Calculate difference: __________ bytes (must be < 30KB)
5. Let system run for 30 minutes with publishing active
6. Check heap every 5 minutes:
   - 5 min: __________ bytes
   - 10 min: __________ bytes
   - 15 min: __________ bytes
   - 20 min: __________ bytes
   - 25 min: __________ bytes
   - 30 min: __________ bytes
7. Run memory diagnostics command: `mqtt.memory`

**Expected Result**:
- Initial allocation < 30KB
- Heap stable over time (±2KB)
- No continuous decrease (leak)
- Fragmentation < 50%

**Failure Scenarios**:
- Allocation > 30KB → Exceeds requirement
- Continuous heap decrease → Memory leak
- High fragmentation → Poor memory management

### Test Case 7: Web Configuration Integration
**Objective**: Test MQTT enable/disable via web interface

**Steps**:
1. Navigate to MQTT settings page
2. Disable MQTT (uncheck "Enable MQTT")
3. Save configuration
4. Verify in Serial: `[INFO] MQTT: Disabled`
5. Check MQTT Explorer - client disconnected
6. Re-enable MQTT via web
7. Save configuration
8. Verify reconnection in Serial
9. Change publish interval to 30 seconds
10. Verify messages now arrive every 30 seconds

**Expected Result**:
- Clean disconnect when disabled
- No crashes when toggling
- Settings persist after reboot
- Publish interval change takes effect

**Failure Scenarios**:
- Crash when disabling → Cleanup issue
- Settings not saved → Persistence problem
- Can't re-enable → State machine stuck

### Test Case 8: Modbus Coexistence
**Objective**: Verify no interference with Modbus operations

**Steps**:
1. Connect Modbus master/simulator
2. Enable MQTT and verify connected
3. Start continuous Modbus polling (100ms intervals):
   - Read holding registers 0-59 (temperatures)
   - Read input registers 100-159 (alarms)
4. Monitor for 10 minutes:
   - Modbus response times: __________ ms average
   - Modbus timeouts: __________ count
   - MQTT messages sent: __________ count
5. Disable MQTT
6. Continue Modbus polling for 5 minutes
7. Compare Modbus performance metrics

**Expected Result**:
- Modbus response time < 50ms with MQTT active
- No increase in Modbus timeouts
- Both protocols work simultaneously

**Failure Scenarios**:
- Modbus timeouts increase → MQTT blocking
- Response time > 100ms → Performance impact
- Modbus stops working → Critical failure

## Performance Tests

### Metrics to Monitor
- **Connection Time**: Time from enable to connected state
  - Target: < 2 seconds with good network
- **Message Latency**: Time from publish call to broker receipt
  - Target: < 100ms for QoS 0
- **CPU Usage**: Loop execution time with MQTT active
  - Target: < 5% additional overhead
- **Memory Stability**: Heap variation over 24 hours
  - Target: < 2KB variation
- **Message Throughput**: Sustained publishing rate
  - Target: > 10 messages/second capability

### Performance Test Procedure
1. Enable performance monitoring in Serial
2. Run stress test: `mqtt.test`
3. Monitor metrics for 1 hour
4. Generate performance report: `mqtt.stats`

## Rollback Testing
**Objective**: Verify system continues working when MQTT disabled

**Steps**:
1. With MQTT active and publishing, disable via web
2. Verify:
   - System continues normal operation
   - Temperature monitoring active
   - Alarms still trigger
   - Web interface responsive
   - Modbus fully functional
3. Check memory released (heap increases)
4. Reboot device with MQTT disabled
5. Verify boots normally without MQTT

**Expected Result**:
- Seamless transition to non-MQTT operation
- All other features unaffected
- Memory properly released

## Error Injection Testing

### Test Case E1: Invalid Broker Address
1. Configure non-existent broker address
2. Enable MQTT
3. Verify appropriate error in Serial
4. System remains stable

### Test Case E2: Wrong Credentials
1. Configure incorrect username/password
2. Verify authentication error logged
3. Verify reconnection with backoff

### Test Case E3: Network Loss During Publishing
1. Queue 10 messages rapidly
2. Disconnect WiFi mid-publish
3. Verify messages queued (not lost)
4. Reconnect WiFi
5. Verify queued messages sent

### Test Case E4: Malformed Configuration
1. Set port to 99999 via API
2. Verify validation rejects configuration
3. Previous valid config retained

## Post-Test Cleanup

2. Clear MQTT configuration:
   - Broker: (empty)
   - Username: (empty)
   - Password: (empty)
3. Reboot device
4. Verify clean state
